# Player Game Fact period aggregation: read-only 7/14/30-day windows

`PlayerPeriodService` takes a canonical `playerId`, an explicit JST baseball `asOfDate`, and `period: "7d" | "14d" | "30d"`. Each range includes its as-of date and the preceding 6, 13, or 29 **calendar** dates. For `2026-09-24`, the ranges begin `2026-09-18`, `2026-09-11`, and `2026-08-26`. Date-only UTC arithmetic avoids device timezone/DST shifts; the dates themselves are Japan baseball dates. This is deliberately different from `AnalysisQuery`'s as-of convention, which excludes its reference day. An app-facing caller must supply a completed as-of date and keep Analysis' previous-day cutoff. There is no UI route or cache in this slice.

The existing `NpbRepository.findBattingByPlayer` / `findPitchingByPlayer` methods each issue one `player_id` + joined `npb_games.game_date BETWEEN from AND to` read. The separate `NpbPeriodCoverageRepository` reads dated ingestion evidence. Pass both readers to `PlayerPeriodService`; omitting the coverage reader explicitly yields `unavailable` coverage, not a false complete claim. The service hands validated Domain Facts to pure `aggregateBatting` / `aggregatePitching`. No SQL aggregation, provider fetch, migration, Derived write, or Fact write occurs. Repeating the call after an upserted correction recomputes from current Facts.

Every counting metric has `{value,status,observedFacts,factCount}`. `complete` means all retrieved rows supplied that field, `partial` means only some did, and `unavailable` means none did. A partial/unavailable count has `value:null`; an observed zero remains zero. A rate is reported only when all inputs are complete and its denominator is positive. Overall `dataStatus` is unavailable with no Fact rows and partial if any metric cannot be established; it describes *retrieved field quality*, not whether every date's scheduled games was ingested.

`coverage` is a separate league-wide collection proof for the same `from..to`: `complete`, `partial`, `unknown`, or `unavailable`. The read-only adapter makes three bounded range queries for the latest Day run per date, the `games` ingestion stage, and final Games joined to Game completeness. A date is complete only when Day run and Game enumeration stage are complete, reported final/complete counts match actual final Games, and every final Game has complete batting, pitching, and Game gates. An explicit `no_games` Day run with zero actual final Games is covered; an absent player Fact is never evidence of a missing day. Known partial/failed runs, stages, or Games make period coverage `partial`. Missing Day metadata or an unproven rest day makes it `unknown`. Missing/failed coverage access makes it `unavailable` while the Fact-derived metrics remain available. Lists of final-Game, complete-Game, no-Game, partial, and unknown dates explain the status. This conservative league-wide measure avoids claiming a team-specific complete span without reliable roster/transfer history; a future HOT ranking can exclude or demote non-complete coverage, but HOT rules are out of scope.

Batting counts: G, PA, AB, R, H, 2B, 3B, HR, RBI, BB, HBP, SH, SF, SO, SB, CS. `G` is the count of distinct Game IDs even with 0 PA/AB; two doubleheader Game IDs count twice. AVG=`H/AB`. OBP=`(H+BB+HBP)/(AB+BB+HBP+SF)`; SH is excluded from its denominator. Singles=`H−2B−3B−HR`, total bases=`H+2B+2×3B+3×HR`, SLG=`TB/AB`, OPS=`OBP+SLG`. Missing extra-base components never become inferred zeros. Internal rates remain unrounded; the existing Japanese Formatter controls display precision.

Pitching counts: distinct G, Fact-row appearances, GS, integer outsRecorded, BF, H, HR, SO, R, ER, pitchCount, W/L/HLD/SV and `walksAndHitByPitch`. ERA=`ER×27/outs`, K/9=`SO×27/outs`. Zero outs makes both rates unavailable. WHIP is `(H+standalone BB)×3/outs` **only** when every Fact supplies standalone BB. Current nf3 pitcher Facts generally carry combined BB+HBP, so WHIP is unavailable; BB/9 is not exposed. Do not use combined 四死 as BB.

## Read-only proof on 2026-09-25

The Turso dashboard SQL console was used with `SELECT` only for the inclusive window `2026-09-18..2026-09-24`. Before/after Remote counts stayed `player_game_batting=244`, `player_game_pitching=79`, `npb_games=30`, `source_entity_mappings=285`. The local development DB also stayed `131/42/25/178` for these tables. `tests/player-period.test.ts` includes minimal captured Turso Fact values and checks the pure engine against independent hand totals. This is a captured-row Remote proof; the service was **not** connected live to Turso from the local process because its credentials were unavailable locally.

For this extension, fresh read-only Turso console queries over the wider `2026-08-26..2026-09-24` range again returned exactly the same two batting Facts for 中島 and two pitching Facts for 上原, with the same field values below; the remote protected counts remained `244/79/30/285` before and after. Turso Day runs and Game-enumeration stages were complete for 9/23 and 9/24, and all 6 and 2 respective final Games had complete batting/pitching gates. Earlier 9/20–22 final Games had no complete Game gates and earlier dates lacked Day-run proof. Thus 7d, 14d and 30d all correctly report collection coverage `unknown` while preserving the Fact-derived summaries. The tests replay these captured rows for all three windows; the local process still did not receive Turso credentials, so live service-to-Turso execution remains unverified.
