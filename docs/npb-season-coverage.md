# NPB season metadata and collection coverage

The 2026 first-team **regular season** is version-controlled in `src/data/npb-season-metadata.ts`, not inferred from the first locally stored Game. This is a small, manually verified calendar record, not an automated NPB page provider or a license to republish NPB site content. The metadata records league, season, competition type, start/end, end verification state, source URLs, method, UTC verification time, and a limitation note. The official [March schedule](https://npb.jp/games/2026/schedule_03_detail.html) lists all six opening games on **2026-03-27**. The [October schedule](https://npb.jp/games/2026/schedule_10_detail.html) lists **2026-10-07** as its latest regular-season fixture at the time of manual review on 2026-09-25. October 7 is a **scheduled endpoint**, not a verified final played date: postponements or newly listed makeup games require a reviewed config update. The metadata has `endDateStatus: scheduled` until that review. Do not silently infer a final date from a sparse local Game table.

`season` resolves from 2026-03-27 through the earlier of the requested JST as-of date and the recorded endpoint. Before opening day it produces an empty result without querying player Facts; after the endpoint it clamps. Only rows with the selected `npb_games.season` are read. The existing Game schema has no competition type, so the date bounds exclude preseason and the currently scheduled postseason but cannot classify any anomalous Game mislabeled within that range. This is a limitation to revisit before ingesting additional competition types. Other years require separately reviewed metadata.

Fact availability is independent: `NpbRepository.findPlayerFactAvailability(playerId, season)` reads the earliest/latest saved batting or pitching Game date for a canonical player and season. Neither date proves the official opener or complete history. For 中島大輔 and 上原健太, the currently published 2026-09-24 summaries use two saved Facts each; their Season window begins March 27, while their Fact values come only from saved rows. The first documented full-day complete evidence is the manually verified 2026-09-23 slate; the 2026-09-24 slate is also complete. Earlier dates must remain `unknown` until verified daily Game enumeration and all final-Game gates are present. This operational date is documentation, not a hard-coded shortcut in the coverage evaluator.

The existing read-only `NpbPeriodCoverageRepository` uses one bounded range read each for latest Day runs, Game-enumeration stages, and final Games plus Game completeness. `evaluatePeriodCoverage` now returns a per-date calendar with `complete`, `partial`, `failed`, `no_games`, or `unknown` and a numeric summary. A day is complete only with a complete Day run and Game stage, matching final/complete Game counts, and complete batting/pitching/Game gates for each final Game. An explicit zero-final `no_games` run is covered. Known partial/failed evidence makes a period `partial`; absent evidence makes it `unknown`; unavailable metadata access makes it `unavailable`. A player's absence does not change league-wide collection coverage. Metric completeness remains separate and may be complete when period coverage is unknown.

All five periods use this calendar. Re-reading after a verified backfill can change coverage from `unknown` to `complete` without changing formulas or writing Derived data. A future HOT eligibility policy can consume `coverage.status` and the summary but is not implemented here. Viewing a Player remains read-only. Version-controlled metadata was chosen over a new DB migration because the calendar changes only a few times per year, review provenance is visible in Git, and the existing Vercel read-only API can consume the same checked-in values; changes require code review and redeployment.

Rollback: revert the metadata and resolver change, plus calendar fields and UI wording, then redeploy the read-only API and Pages client together. Fact tables, collector, scheduled workflows, and backup remain untouched.
