# NPB season metadata and collection coverage

The 2026 first-team **regular season** is version-controlled in `src/data/npb-season-metadata.ts`, not inferred from the first locally stored Game. The reviewed range is **2026-03-27–2026-10-08**, checked October 13 using official calendar/competition evidence and the existing nf3 Game/Day. It is a small source-verified calendar record, not an automated NPB page provider or permission to republish official statistics. Metadata records league, season, competition, start/end, end verification state, URLs, method, verification time and limitations. [March schedule](https://npb.jp/games/2026/schedule_03_detail.html) supports the opener. [October schedule](https://npb.jp/games/2026/schedule_10_detail.html) and [October 8 Game](https://npb.jp/scores/2026/1008/t-s-25/) explicitly support the newly admitted Regular fixture; October 10 is CS First Stage. The old September 25 review stopped October 7 and is superseded. **October 8 remains a provisional calendar endpoint** (`endDateStatus: scheduled`, season `in_progress`), not proof of whole-season completion. Further makeup dates require reviewed updates. Verification is Codex-assisted, not human-reviewed. See [individual integrity audit](npb-data-integrity-2026-10.md).

`season` resolves from 2026-03-27 through the earlier of the requested JST as-of date and the recorded endpoint. Before opening day it produces an empty result without querying player Facts; after the endpoint it clamps. Only rows with the selected `npb_games.season` are read. The existing Game schema has no competition type, so the date bounds exclude preseason and the currently scheduled postseason but cannot classify any anomalous Game mislabeled within that range. This is a limitation to revisit before ingesting additional competition types. Other years require separately reviewed metadata.

Fact availability is independent: `NpbRepository.findPlayerFactAvailability(playerId, season)` reads earliest/latest saved canonical batting/pitching Game dates. Neither proves the opener or complete history. The historical September 24 two-Fact examples and September 23 first full-Day proof are earlier implementation evidence, not current coverage. October 13 read-only audit of the corrected range gives **196 dates / 165 complete / 25 no_games / 6 partial / 0 unknown / 0 failed**, with **9 pending saved Games**. October 8 already has 36 batting/9 pitching Facts and complete Game/Day evidence, but its scheduled backup failed. No evidence row was upgraded or repaired by the calendar correction. Missing evidence must still remain unknown/partial as evaluated, without a date shortcut.

The existing read-only `NpbPeriodCoverageRepository` uses one bounded range read each for latest Day runs, Game-enumeration stages, and final Games plus Game completeness. `evaluatePeriodCoverage` now returns a per-date calendar with `complete`, `partial`, `failed`, `no_games`, or `unknown` and a numeric summary. A day is complete only with a complete Day run and Game stage, matching final/complete Game counts, and complete batting/pitching/Game gates for each final Game. An explicit zero-final `no_games` run is covered. Known partial/failed evidence makes a period `partial`; absent evidence makes it `unknown`; unavailable metadata access makes it `unavailable`. A player's absence does not change league-wide collection coverage. Metric completeness remains separate and may be complete when period coverage is unknown.

All five periods use this calendar. Verified backfill evidence can change evaluated coverage without changing formulas. HOT eligibility and its separate Production Gate are now implemented; the Gate remains closed for insufficient batting sample and scheduled/exported backup proof. Ranking remains closed for partial Season coverage and its unchanged publication conditions. Calendar expansion cannot open either Gate. Player views stay read-only. Version-controlled metadata avoids a DB migration, preserves review provenance and is shared by Vercel readers/generators. Boundary changes require code review and coordinated projection publication; never update just one projection or call a manual backup drill Scheduled proof.

Rollback: revert the metadata and resolver change, plus calendar fields and UI wording, then redeploy the read-only API and Pages client together. Fact tables, collector, scheduled workflows, and backup remain untouched.
