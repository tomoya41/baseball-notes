# NPB HOT static payload staging

`NpbHotPayload` schema version **1** is a small, validated presentation projection of the existing seven-calendar-day Batch and HOT Candidate Engine. `effectiveDate` is the inclusive Japan baseball date at the end of the window; `generatedAt` is the distinct UTC creation instant. The period is exactly `effectiveDate - 6 days` through `effectiveDate`. The JSON includes readiness, category readiness, Coverage status and counts, candidate/eligible counts, and at most five ranked entries per category. Each entry carries canonical Player ID, rank, role, OPS or ERA, sample, a deterministic reason and rank inputs; optional reviewed display name/team/position can be joined before generation. It contains no Game Facts, WHIP, source URL or credential.

The candidate evaluator remains the sole authority for Coverage, Metric and Sample eligibility and tie-break order. The generator adds only the operational scheduled-production-evidence gate and projects the eligible results. Overall readiness requires complete Batch Coverage, a positive eligible count in **each** of batter, starter and reliever, and verified full-day scheduled-production evidence. Category readiness is reported independently. A mixed set (for example, eligible batters and starters but no relievers) is overall `not_ready`: **all three public arrays remain empty**. This prevents an accidental partial Home rollout; the category fields retain enough information to support a separately reviewed staged rollout later. Manual diagnostics always pass `scheduledProductionEvidence: false`, so a manual run cannot impersonate unattended production proof.

The strict schema checks version, dates, exact 7d bounds, readiness consistency, sequential ranks, duplicate Player IDs *within each category*, rank-input/metric agreement, deterministic order via the Candidate Engine comparator, non-null finite published values, and reason/primary-metric agreement. A two-way Player may legitimately appear in batting and pitching categories. Unknown fields, including a WHIP or secret field, are rejected. A fixed `generatedAt` and unchanged input produce byte-identical JSON regardless of input candidate order.

`writeNpbHotPayloadAtomically` validates the object, writes a unique temporary file beside the destination, reads and validates that file, then renames it over the destination. Invalid input leaves the previous file intact; temporary files are removed. The command `npm run generate:npb:hot:diagnostic -- --date=2026-09-24` writes **only** `.data/hot-diagnostics/npb-hot-7d.json`, which Git ignores. The existing manual-only read-only period-batch Action can run the same diagnostic against Turso; it does not upload or publish the file. The independent publish command also uses SELECT-only access and compares protected Fact/Game/mapping counts before and after. Daily ingestion does not call the generator.

## Independent static delivery

`npb-hot-publish.yml` is a manual-only workflow, separate from the Daily Collector. It reads stored Facts and Day evidence through a SELECT-only client, verifies the latest scheduled GitHub Action and its encrypted Artifact, aggregates the seven-day Batch, validates the HOT contract, and atomically stages `data/npb/hot/latest.json`. The public Pages artifact contains that small JSON, the current validated standings JSON, and the app; it never contains Fact rows or credentials. The same Pages deployment concurrency group serializes the two full-site deployments. A publish failure leaves the previous Pages deployment intact. The HOT workflow has no nf3 access and no Turso write.

Pages deployment replaces the entire site. The Daily workflow's **build/publish step only** therefore fetches the already public HOT JSON with a cache-busting query, validates its complete schema, and carries it into the next site artifact. Missing or invalid HOT data is skipped without failing daily ingestion or publishing. It never generates HOT, changes Collector behavior, or opens the gate. Home rejects a ready payload whose effective date differs from the preceding JST day; it shows an update state instead of a stale ranking. A validated last-successful device cache can cover an HTTP failure, but the same date guard still applies.

When Production readiness is closed, the public JSON has empty batting/starter/reliever arrays and retains only period, counts, readiness reasons and coverage. Home shows a quiet preparation state and has no sample-ranking fallback. When all three categories are ready, the same payload renders the first three of each Top 5 with verified Player name/team, OPS or ERA, sample and canonical Player link. Missing display identity closes publication rather than exposing IDs as names. The source metadata is joined in one batch read, so Home never queries Turso.

Operator: dispatch `Publish NPB HOT static payload` on `main`, optionally with `as_of_date`. Verify the Action's schema check, Pages deployment and actual public HTTP response at `https://tomoya41.github.io/baseball-notes/data/npb/hot/latest.json`. A Daily Collector run is not evidence of HOT publication; a manual HOT publication is not evidence of an unattended Daily Collector success. The future Daily-success trigger may call this independent workflow after the ingestion/readback gate passes, but is **not enabled** here. Rollback disables the HOT workflow and removes the Home adapter; the existing standings endpoint and permanent Facts remain intact.
