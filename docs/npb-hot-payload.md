# NPB HOT static payload staging

`NpbHotPayload` schema version **1** is a small, validated presentation projection of the existing seven-calendar-day Batch and HOT Candidate Engine. `effectiveDate` is the inclusive Japan baseball date at the end of the window; `generatedAt` is the distinct UTC creation instant. The period is exactly `effectiveDate - 6 days` through `effectiveDate`. The JSON includes readiness, category readiness, Coverage status and counts, candidate/eligible counts, and at most five ranked entries per category. Each entry carries canonical Player ID, rank, role, OPS or ERA, sample, a deterministic reason and rank inputs; optional reviewed display name/team/position can be joined before generation. It contains no Game Facts, WHIP, source URL or credential.

The candidate evaluator remains the sole authority for Coverage, Metric and Sample eligibility and tie-break order. The generator adds only the operational scheduled-production-evidence gate and projects the eligible results. Overall readiness requires complete Batch Coverage, a positive eligible count in **each** of batter, starter and reliever, and verified full-day scheduled-production evidence. Category readiness is reported independently. A mixed set (for example, eligible batters and starters but no relievers) is overall `not_ready`: **all three public arrays remain empty**. This prevents an accidental partial Home rollout; the category fields retain enough information to support a separately reviewed staged rollout later. Manual diagnostics always pass `scheduledProductionEvidence: false`, so a manual run cannot impersonate unattended production proof.

The strict schema checks version, dates, exact 7d bounds, readiness consistency, sequential ranks, duplicate Player IDs *within each category*, rank-input/metric agreement, deterministic order via the Candidate Engine comparator, non-null finite published values, and reason/primary-metric agreement. A two-way Player may legitimately appear in batting and pitching categories. Unknown fields, including a WHIP or secret field, are rejected. A fixed `generatedAt` and unchanged input produce byte-identical JSON regardless of input candidate order.

`writeNpbHotPayloadAtomically` validates the object, writes a unique temporary file beside the destination, reads and validates that file, then renames it over the destination. Invalid input leaves the previous file intact; temporary files are removed. The command `npm run generate:npb:hot:diagnostic -- --date=2026-09-24` writes **only** `.data/hot-diagnostics/npb-hot-7d.json`, which Git ignores. The existing manual-only read-only period-batch Action can run the same diagnostic against Turso; it does not upload or publish the file. Both local and remote scripts reject non-`SELECT` SQL and compare protected Fact/Game/mapping counts before and after. No Daily Workflow, Pages sequence, Home UI or public HOT endpoint calls this generator.

At implementation (2026-09-26 02:48–02:58 JST), the first full-day Daily Collector scheduled opportunity at 03:37 JST had not arrived: **Scheduled production evidence: pending**. The pre-full-day scheduled run is not accepted as proof. The local 2026-09-24 diagnostic used six Batch reads and zero generator reads, returned `not_ready` with empty rankings, and produced a 700-byte JSON file.

It found 282 candidates, zero complete-Coverage or eligible Players, and emitted zero public entries. Its six Batch queries took 614 ms to read; aggregation 4 ms, HOT evaluation 1 ms, projection/validation 2 ms, serialization under 1 ms, and total 1,207 ms. The JSON was 700 bytes. Future integration can follow successful Daily ingestion and readback with Batch → Candidate → schema validation → atomic publish. Before connecting it, review the eligible cohort size and provide verified display metadata so Home requires no extra DB reads. This task does not connect or enable that sequence.
