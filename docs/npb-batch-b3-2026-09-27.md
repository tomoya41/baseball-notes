## Calendar, Watcher, publication

- Canonical Game retains date, scheduledTime (nullable HH:mm), canonical home/away, status, venue, gameNumber, score. `gameNumber` is part of canonical identity; doubleheaders remain distinct. The operational timezone is explicitly Asia/Tokyo, not inferred from the runner locale. No live inning/state or appearance-order data is invented.
- All sync ranges use the same paired twelve-team published-schedule parser: season metadata range, monthly next45 days, weekly next14, daily today; clamp at metadata end. Paired start times must agree. A disappeared Game is not a cancellation; final→nonfinal is rejected. Future confirmed schedule does not make future Coverage complete.
- Sync clocks: daily09:27, weekly Monday08:37, monthly first08:47 JST. Season bootstrap is manual. `17 * * * *`, `timezone: Asia/Tokyo` checks hourly. [GitHub official schedule documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) supports the IANA timezone field.
- monitorAfter is canonical start+120min (configurable0–1440). Missing start stays unmonitored rather than inventing15:00/20:00. Confirmed no-games, unconfirmed schedule, already published or before monitoring produce no nf3 request.
- Only due Games use paired team pages; explicit result ○/●/△ plus matching score is required for final. No player detail while ongoing. Newly final/currently unvalidated Games take existing atomic full-authoritative ingestion. Completed current Facts skip detail collection; partial/temporary failures remain retryable. All final/postponed/canceled is terminal; suspended/unknown is not.
- Before Day finalization, all twelve schedules are reconciled once more to detect additions/changes, then current Facts are revalidated. Score alone never sets complete. Source standings W/L/T must independently match the paired final schedule before capturing EOD date.
- Publication only after newly complete Day; generation uses existing Season/directory/HOT/standings paths. Recent/Game/Analysis use existing remote read APIs with the captured completed date. Ranking/HOT gates are unchanged. Failure before deploy retains Facts, failure after deploy before mark is retried; **exactly-once deployment across network failure cannot be guaranteed**, but a marked successful publication has no routine duplicate deploy.
- All DB-writing/publishing workflows share `daily-npb-collector-and-pages`, cancel-in-progress false. Daily03:37 and Freshness12:17 are unchanged. Daily skips the source/build/deploy after an EOD publication marker and current-Fact validation; invalid/missing EOD publication goes through normal safety ingestion. Seven-day encrypted portable exports are generated on publishing Runs; raw export is never public.
- `NPB_EOD_ENABLED` is the reversible operational rollout switch. The new schedules do not establish Scheduled production proof. No Infrastructure Phase reassessment or forced HOT/Ranking opening.

## Observability, load and failure boundaries

Run reports include no-op/active reason, scheduled/monitored/terminal/new-final/full-collection/failed-collection counts, HTTP/unique-pages/retry/cache-hit/bytes, SQL reads/writes, source-check start, finish/elapsed and publishRequired/publishPerformed. Deploy success is separately recorded. Runner start is captured before checkout; GitHub run created_at comes from the official Actions API. GitHub supplies cron, not the intended trigger instant, so expectedScheduledAt is the latest inferred cron clock before run creation, **delayIsLowerBound=true**. Run creation→runner and runner→source→finish are distinguishable; an hourly Run delayed several hours cannot prove exact original trigger time.

Status-only run request bound is **2–12 published team pages**, not Player pages; finalization adds up to twelve pages with same-run dedupe. Schedule sync takes twelve pages, standings reconciliation one root page in addition to cached schedules. Polite serial1000ms gaps, timeout15s, maximumtwo HTTP attempts, retry only429/5xx/network, no permanent404/oversize/invalid-encoding retry. Full-detail request counts depend on newly final participants and existing shared-page cache, never every-hour all-player recollection.

Typical simulation, all6 Games start13:00 and end16:00: checks15:17+16:17 → up to24 status requests, finalization uses already cached12 schedules, standings adds1 → **25** status/root requests plus daily12 sync; full collection once/Game. All6 start18:00 and end21:00: same bound20:17+21:17. Mixed3 day/3night: up to24 subset checks plus up to6 additional finalization schedule pages and1 root → **31**, plus daily12 sync. These are **assumptions**, not measured provider update timings; extra delay adds up to12 schedule requests/active hour. Successful Pages publishes normally1/day; retries can exceed1 after failure. SQL writes are changed canonical headers/new authoritative Facts/identity mappings/Day records and operational ledger, never periodic derived snapshots. Public Actions runner allocation remains hourly even on no-op; public repository standard-hosted runner usage is not additional monthly paid infrastructure, but it is not zero CPU.

No guaranteed **actual-end→0–60min** SLA: the design can react at the next hourly clock **after source updates**, plus Actions queue, collection and build latency. Source update latency was not established. Source closure risk and explicit shortened evidence remain independent data blockers.
