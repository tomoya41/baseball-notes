# NPB Player Game Log

The existing canonical NPB Player page shows a separate **試合別成績** section below Recent. It reads only saved `player_game_batting`, `player_game_pitching`, `npb_games`, and Player Master identity. Recent period aggregation and Profile Master remain separate. Opening or expanding a log never contacts nf3 and never writes a Fact, derived table or cache table.

`GET /api/npb/game-log?playerId=<canonical UUID>&limit=10&offset=0` runs on the existing Vercel read-only service. Known Players with no Facts receive two empty arrays; unknown IDs receive 404. The server makes three SELECTs for a known Player: Master existence, Batting joined to Game, and Pitching joined to Game. Each role has its own descending date/time/game-number/Game-ID order and the same configurable limit (1–50) and offset. A same-day doubleheader keeps two Game IDs. An opponent/team mismatch stops the response instead of inventing a matchup. The HTTP client validates the response and checks the requested identity and pagination before it reaches the UI. The public response excludes raw HTML, source IDs/URLs and credentials. `Server-Timing` reports database read and JSON serialization duration for operational measurements.

Each row uses the Fact's team ID and the Game's home/away IDs for the opponent, side, score and team-side result. A result is only computed for a final Game with both scores. Null Fact metrics stay null and render as `—`; a recorded zero remains zero. Pitching uses `outsRecorded` and formats baseball innings only for display (`17 → 5.2`, `1 → 0.1`, `2 → 0.2`). Pitcher `walksAndHitByPitch` is labeled **四死**, never BB; WHIP is absent. The first line is compact; saved detail metrics expand locally without another request. The label **保存済みデータの最新試合・登板** avoids implying complete Season coverage. Master-only Players show **保存済みの試合別成績はありません**, distinct from an API error.

`npm run vercel-build` builds both the existing Recent route and the new Game Log route. The output under `api/npb` is ignored by Git. The GitHub Pages app uses the same public API base URL as Recent; the Turso read-only token remains in Vercel server environment variables. Deploy Vercel first, then publish the Pages app by the existing whole-site manual workflow while preserving standings, HOT and Directory payloads. Do not change the Daily Collector or Freshness workflow for this feature.
